# Contributing to SchoolFactors

Thanks for helping make California school data more transparent. Everything here —
pipeline, analysis, site, and the data-quality findings — is open, and every number
on the site must be reproducible from this repository.

## Getting set up

```bash
git clone https://github.com/ssorkin/schoolfactors
cd schoolfactors
uv sync --extra dev          # Python 3.12+ pipeline (managed by uv)
cd site && npm install       # SvelteKit site (Node 20+)
```

Pipeline (from the repo root):

```bash
uv run sf acquire            # download all source data (~5 GB), record checksums
uv run sf ingest             # normalize to Parquet + build DuckDB views
uv run sf check              # data-quality checks -> DATA_QUALITY.md
uv run sf analyze            # fit the models, render figures, write stats
uv run sf export             # generate site/static/data/ JSON for the site
uv run pytest                # tests
uv run ruff check src tests  # lint (line length 100)
```

Site (from `site/`): `npm run dev` for local development, `npm run build` for the
static build. The site is fully static — no API; all data comes from the JSON that
`sf export` writes to `site/static/data/`.

Heads-up on acquisition: CDE's web application firewall rate-limits aggressively.
The downloader paces itself, detects block pages, and aborts rather than hammering;
if you get blocked, wait a few hours and re-run — it resumes where it left off.

| Path | Contents |
|---|---|
| `src/schoolfactors/acquire/` | manifest-driven downloaders (CAASPP, CDE, Dashboard) |
| `src/schoolfactors/ingest/` | era-aware parsers → Parquet, DuckDB view builder |
| `src/schoolfactors/quality/` | data-quality checks + report generator |
| `src/schoolfactors/analysis/` | models, covariates, cohorts, neighbors, site export |
| `manifests/` | provenance: URL, version, sha256 for every source file (committed) |
| `known_issues/` | registry of documented problems in the source data (committed) |
| `curated/` | community-maintained facts CDE doesn't publish (committed, cited) |
| `analysis/` | writeups and figures |
| `site/` | the schoolfactors.org SvelteKit site |
| `DATA_QUALITY.md` | generated by `sf check` — regenerate, don't hand-edit |

## The rules that keep the numbers honest

These are non-negotiable in review (full detail in `CLAUDE.md`):

1. **Never hardcode versioned source URLs.** CDE silently reposts files as
   `-v2`/`_v2`; downloaders scrape landing pages and record what they got in
   `manifests/`.
2. **Never sum across CAASPP student groups** (they overlap), and always filter CDE
   long files on `AggregateLevel` / `Charter='All'` / `DASS='All'` at aggregate
   levels — otherwise totals inflate up to 9×.
3. **Suppressed values are data.** `*`/blank/n<11 stay null; never coerce to 0, and
   never reconstruct a suppressed subgroup by subtraction below n=11.
4. **Percentages are never averaged** — go through counts (see the complement
   computation in `analysis/cohorts.py` for the pattern).
5. **Mean scale score (or its standardized form), never percent-proficient, is the
   modeling metric.** Percent-met appears only as a clearly-labeled display value.
6. **Data problems are documented, not patched.** If you find an inconsistency, add
   a `known_issues/*.yaml` entry (with evidence) and, where possible, a check in
   `quality/checks.py` that detects it. The 2015 enrollment-definition issue is the
   template.
7. **Site language discipline:** correlations, not causes; "schools serving similar
   students," never "better schools"; lists with values and intervals, never bare
   integer ranks.

## Contributing curated data

`curated/selective_admissions.yaml` flags schools with exam/criteria-based
admission — something CDE publishes no field for. Entries must be conservative and
verifiable: include the school's CDS code, the kind (`exam` / `criteria` /
`lottery+`), a one-line factual note, and a `source` URL that documents the
admission process (school or district page preferred). PRs that add entries without
a source, or that characterize a school beyond what the source supports, will be
asked to revise.

## Adding a data source

1. Downloader in `acquire/` (scrape the landing page; record manifests; respect the
   WAF pacing helpers in `acquire/base.py`).
2. Parser in `ingest/` (nullable strings first, snake_case columns, zero-padded CDS
   key; see `ingest/cde.py` for the generic tab/xlsx readers — note the UTF-16 and
   deep-header quirks already handled there).
3. A `quality/` check if the source has failure modes worth catching.
4. If it feeds the site, wire it through `analysis/export.py`.

## Statistical changes

Model changes need more than working code: run `sf analyze` and include the printed
diagnostics in your PR (cross-source correlations, sensitivity table, falsification
test). A change that improves one metric but degrades ranking stability across
specifications needs discussion, not just a diff. The methodology writeup
(`analysis/first_analysis.md`) must be updated in the same PR as the change it
describes.
